# Architecture

Zorvik is a Rust workspace with a React UI in a Tauri 2 shell. Almost everything lives in Rust: networking, files, scripts, load tests, servers and the AI agent tools. The UI renders the state and calls one RPC entry point.

```
app/                 React UI (Vite, TypeScript, Tailwind, CodeMirror)   ─┐
app/src-tauri/       Tauri shell: one `rpc` command, events, menus        │  rpc(method, params)
crates/devbridge/    The same API over HTTP, for a browser (dev, E2E)    ─┘
      │
crates/api/          RPC dispatcher and app state: in-flight requests, stream sessions, cookie
      │              jars, history, secrets, file watcher, runner, scenarios, load runs, servers, agents
crates/workspace/    Workspace on disk, variables, auth and OAuth 2.0, request resolution,
      │              history (SQLite), settings, secret store
crates/formats/      Data model (YAML files) and import/export: cURL, Postman, OpenAPI, Google Discovery,
                     AWS Smithy, code in 16 languages
crates/script/       Sandboxed JavaScript (QuickJS) for pre-request and post-response scripts
crates/load/         Load generator: own runtime, pooled client, HdrHistogram metrics, reports
crates/servers/      Servers the user runs: mock HTTP, MCP, WebSocket, Socket.IO, SSE, TCP, UDP, DNS, TCP relay
crates/engine/       Networking only: HTTP/1.1, HTTP/2, HTTP/3, TLS, proxy, WebSocket, SSE,
                     TCP/UDP/DNS/MQTT/gRPC/Socket.IO/MCP clients, GraphQL subscriptions,
                     cookies, decoding, timing, network tools, certificate decoding
crates/cli/          `zorvik`: run, load, serve and mcp (the command line inside every install)
crates/mcp/          Zorvik's own MCP server for AI agents: the stdio bridge (`zorvik mcp`) and the app's listener
crates/testkit/      Local test servers used by the tests (HTTP, TLS, proxy, OAuth, GraphQL, gRPC),
                     and the practice servers of Training Bootcamp labs
crates/academy/      Training Bootcamp: the course (lessons, labs, quizzes as files), patterns, progress rules
```

## Design rules
- **The engine knows nothing about files or the UI.** Callers hand it fully resolved requests.
- **One entry point.** `Api::call(method, params)` in `crates/api` serves the desktop app (Tauri IPC) and the dev bridge (HTTP), so browser E2E tests run the production code path. The methods are the arms of the `match` in `Api::dispatch`. The CLI reuses the same modules (runner, scenarios, load tests, servers) directly.
- **Types are generated.** Rust structs with `#[derive(TS)]` are written to `app/src/bindings/*.ts` by `cargo test`. Never edit them by hand; CI fails when they are out of date.
- **Events flow Rust → UI** through an `EventSink` (the `zv:event` event in Tauri): stream messages, server traffic, run progress, file changes, agent activity. Sinks batch them every 25 ms so floods don't freeze the webview.
- **Big data stays in Rust.** The UI gets a display copy of a response (text up to 10 MB, images up to 8 MB); "Save to file" writes the full body from Rust.
- **Secrets never go into workspace files.** Secret variable values, cookies and OAuth tokens live in the app data folder.
- **Workspace files are untrusted input.** They come from Git: symlinks are not followed, sizes and depths are capped, IDs are validated, body files must be inside the workspace unless the user allows others.

## Request flow (HTTP)
1. The UI calls `http.send {requestId, request, path}`.
2. Pre-request scripts run: workspace, then folders (outer to inner), then the request. They may change the request and set variables.
3. The request is resolved: variables, inherited headers and auth from folders and the workspace, body encoding. Signing auth (AWS SigV4, OAuth 1.0a, JWT, Hawk, Akamai EdgeGrid, ASAP) signs the final method, URL, headers and body here, fresh for every send (`crates/workspace/src/signing.rs`, algorithms in `crates/workspace/src/auth/`).
4. OAuth 2.0: a cached token is used, refreshed or fetched.
5. `engine::Client::send`: DNS, TCP (Happy Eyeballs), proxy tunnel, TLS, HTTP/1.1 or HTTP/2 (or QUIC for HTTP/3), redirects, decoding. Digest and NTLM are a `ChallengeAuth` in the request options: when the server answers 401 with a challenge, the engine sends the request again with the answer on the same connection (NTLM forces HTTP/1.1).
6. Post-response scripts run the tests and fill the response's console. A request imported from an OpenAPI document the workspace keeps also gets a "Matches the API spec" test (see below).
7. A history row is written. The response goes back with timing, TLS details, cookies, the headers really sent and the script results.

Every step that sends something also writes to the app's console (see [Console](#console)).

## Live sessions
WebSocket and SSE requests have their own session APIs (`ws.*`, `sse.*`). TCP, UDP, MQTT, Socket.IO and GraphQL subscriptions share one (`socket.*` in `crates/api/src/sockets.rs`): `socket.connect` resolves the request, opens the engine's session for its kind, and forwards its `SocketEvent`s to the UI; `socket.send` passes `SocketOutgoing` messages (text, binary, MQTT publishes, Socket.IO emits).

- **What live sessions share** (`crates/api/src/live.rs`): `MessageLog`, the last 1000 text and binary messages of a WebSocket or socket session (at most 8 MB) that waits and agents read, with each message's Socket.IO event or MQTT topic; `run_steps`, which runs a request's on-connect steps (send a saved message, wait for one that matches, keep sending one) in the backend, and `run_steps_once` for collection runs; `spawn_repeat` for repeating sends; and `transcript`, the JSON body of a run's response. A wait reads the log from the last message sent before it, so a reply that arrived before the wait started counts. Repeating sends render the message's variables each time and stop with the connection.
- **WebSocket** (`crates/api/src/websocket.rs`): `ws.connect`, `ws.send`, `ws.close`, `ws.repeat` and `ws.stopRepeat`. After connecting, `run_steps` runs `websocket.onConnect`; the steps' progress goes to the UI log as `WsEvent::Info` notes. The engine's `WsEvent::Closed` carries the close code's meaning for the log.
- **Matching** (`crates/formats/src/matching.rs`): single-value JSON paths (`$.items[0].id`, `[-1]`, `['odd key']`) and `MessageMatcher` (any, contains, exact, regex, or a JSON condition `$.path`, `== value`, `!= value`, compared as text). Server reply rules, WebSocket wait steps and agents' waits use it; load-test captures use its JSON paths. The UI has the same paths and conditions in TypeScript (`app/src/lib/messageMatch.ts`) for the log filter and reply pairing (`replyKey`).
- **Scripts of live connections** (`crates/api/src/message_scripts.rs`): WebSocket and Socket.IO connects run the pre-request chain first (`scripting::pre_request`, shared with sends; it may change the request and set variables, which the connect then resolves with). `MessageScripts` holds the request's `onMessage` scripts, their matchers and the connection's `ScriptVars`; one worker per connection runs the scripts that match each message (`Feed`, fed by the session's event pump, bounded at 1000 waiting) through `run_chain` with `Event::Message`, which gives scripts `pm.message` and records `pm.connection` sends (`ScriptOutput::sends`). The worker sends them on the connection, remembers them so they never run "sent" scripts again, reports notes to the log (live) or tests and console lines (runs, where `Feed::settled` lets the scripts answer before the connection closes), and keeps variables they set (`StreamEvent::VariablesChanged` tells the UI). Other live kinds run no scripts.
- **GraphQL subscriptions** are HTTP requests with a GraphQL body whose operation is a `subscription` (`crates/formats/src/graphql.rs` reads the operation type without a full parser; the UI does the same with graphql-js's lexer). `resolve` adds the subscription's URL and connection params. `crates/engine/src/graphql.rs` speaks `graphql-transport-ws` and `subscriptions-transport-ws` over the engine's WebSocket, and graphql-sse over a streaming POST. Collection runs, the CLI and agents read a subscription to an end like an SSE request (`crates/api/src/sse_read.rs`): results become `next` events, and the response body is the results as a JSON array.
- **Socket.IO** (`crates/engine/src/socketio/`): `packet.rs` encodes Engine.IO 4 and Socket.IO packets (namespaces, acknowledgement ids, binary attachments as placeholders) for both the client and the server. The client runs the same session over WebSocket or long-polling (a GET loop and POSTs through the engine's HTTP client), falling back to polling when the server refuses the upgrade. With `SocketIoConfig.auto_ack` set, the session answers the server's events that ask for an acknowledgement itself. `sockets.rs` runs a Socket.IO request's on-connect steps (`socketio.onConnect`; a wait can name an event, and its pattern is matched against the event's arguments as a JSON array), and `socket.repeat` / `socket.stopRepeat` repeat Socket.IO emits and TCP and UDP sends.

The composer's binary sources build on those sessions. A **file** streams in the backend (`fileStream.*` in `crates/api/src/file_stream.rs`): `fileStream.start` reads the chosen range of the file and sends one chunk per interval on the connection's WebSocket or socket session (as a binary message, an MQTT publish or a Socket.IO emit) or on a gRPC stream (a JSON message with the chunk as base64 in the request's `grpc.chunkField`; the stream's `Settled` counts its sent messages), so a hidden window doesn't slow the pace; progress goes to the UI as `fileStream` events, and closing the connection stops the stream. The **microphone** is captured in the webview (`app/src/lib/mic.ts`): raw formats come from an AudioWorklet (`app/public/mic-worklet.js`) and are resampled and encoded in TypeScript (`app/src/lib/audio.ts`), compressed ones from `MediaRecorder`; each chunk goes out through `ws.send`, `socket.send` or `grpc.send` (gRPC: in the chunk field), one at a time so they arrive in order. The Tauri shell allows the webview's microphone requests; the system still asks the user, and macOS needs `NSMicrophoneUsageDescription` (`app/src-tauri/Info.plist`) and the `audio-input` entitlement (`Entitlements.plist`) under the hardened runtime.

The message log is UI state: its filter, view and reply pairing run in TypeScript. To export it (JSON Lines) or save a binary message, the UI passes the text or bytes it holds to `file.save`, with a path the user picked in a save dialog.

## MCP client
MCP requests (kind `mcp`) talk to MCP servers. `crates/engine/src/mcp/` is the client: `mod.rs` runs a session over a `Link` (outbound and inbound channels) that each transport provides, routes answers to waiting requests by id, answers the server's own requests (`ping`, `roots/list`; sampling and elicitation get `-32601`), and reports every message as an `McpEvent`. `http.rs` is Streamable HTTP (a POST per message, the answer as JSON or an event stream, the session id and protocol version headers, a `GET` stream for the server's messages once initialized, `DELETE` on close) and the older HTTP+SSE transport, which `Auto` falls back to when the first POST gets 400, 404 or 405; both go through the engine's HTTP client, so proxies, TLS settings, cookies and the agent host guard apply. `stdio.rs` starts a program (split like a simple shell line, never through a shell), reads one JSON message per line with a size limit, keeps its standard error as the log, and on close ends its input, waits, then stops its whole process group (`taskkill /T` on Windows).

`crates/api/src/mcp.rs` has the `mcp.*` session RPC (`connect`, `catalog`, `close`, `program`, `trust`) keyed by the tab id. A call is sent like any request (`http.send` → `scripting::send`): on the tab's session when it is open to the same address and transport, otherwise in one go (connect, call, disconnect); the answer becomes an HTTP-like response (the JSON-RPC result or error as the body, status 200 or 500) so scripts, tests, history, runs and agents need nothing new. Workspaces are untrusted, so a program starts only when its fingerprint (SHA-256 of the command, folder and sorted environment) is in `trusted-programs.json` for that workspace; `zorvik run` needs `--allow-programs`, and agents are asked every time (`Programs::Approved`). In the app, a program also gets the login shell's `PATH` (GUI apps start with a short one).

## Workspace format
A workspace is a plain folder of YAML files, meant to be committed to Git.

```
my-api/
  zorvik.yaml              # name, id, workspace variables, default auth and headers, scripts
  environments/
    Dev.yaml
  requests/
    Get status.yaml
    Users/
      _folder.yaml         # optional: order, auth, headers, scripts, docs of the folder
      List users.yaml
  servers/
    Payments mock.yaml     # a server: kind, address, port, TLS and its settings
  scenarios/
    Checkout.yaml          # a scenario: steps (saved requests, flow), variables, docs
    Shop/                  # a folder of scenarios (optional _folder.yaml: name, order)
  loadtests/
    Checkout smoke.yaml    # a load test: requests, model, stages, thresholds
  specs/
    Payments API.yaml      # OpenAPI documents kept by imports (see "OpenAPI")
```

A request file:
```yaml
name: Create user
seq: 2                                  # order in the sidebar
method: POST
url: "{{baseUrl}}/users?notify=true"
headers:
  - key: X-Request-ID
    value: "{{$uuid}}"
body:
  type: json                            # none | json | text | xml | formUrlencoded | multipart | binary | graphql
  text: |
    { "name": "{{name}}" }
auth:
  type: bearer                          # inherit (default) | none | basic | bearer | apiKey | oauth2
  token: "{{token}}"
scripts:
  postResponse: |
    pm.test("Status is 201", () => pm.response.to.have.status(201));
```
Other request kinds add `kind:` (`websocket`, `socketio`, `sse`, `grpc`, `tcp`, `udp`, `dns`, `mqtt`). Default values are left out so files stay small and diffs stay clean.

An environment file marks secrets; their real values stay on each computer:
```yaml
name: Dev
variables:
  - { key: baseUrl, value: "http://localhost:3000" }
  - { key: token, value: "", secret: true }
```

Rules:
- File names come from item names, made safe for Windows and macOS. The display name is inside the file.
- Broken YAML shows up in the sidebar with a warning instead of failing the workspace.
- `zorvik.yaml` carries `version: 1`; a newer format is refused with a clear message.
- Secret values, cookies and tokens are keyed by the workspace `id` **and** its folder, so a copied `id` doesn't unlock another workspace's secrets.

Per-request settings (`settings:`) include `repeat: {condition, intervalMs, timeoutMs}` (collection runs send again until the JavaScript condition holds) and, for SSE requests, `stream: {event, maxEvents, timeoutMs}` (when a run or an agent stops reading). Enabled query parameters live in `url`; switched-off ones in `disabledParams`, and descriptions of enabled ones in `paramDescriptions`.

Requests, folders, the workspace, servers, scenarios and load tests carry `docs` in Markdown. `app/src/lib/markdown.ts` parses it into a small tree that `components/DocsEditor.tsx` renders as React elements: no HTML from the source, links limited to http, https and mailto, no remote images. ```` ```mermaid ```` blocks are drawn by Mermaid (`components/MermaidDiagram.tsx`, loaded on first use) with `securityLevel: "strict"`, so labels are sanitized and nothing in a diagram runs or links. The Training Bootcamp keeps its own lesson renderer (`components/academy/Markdown.tsx`: callouts, diagrams, lab variables).

## OpenAPI
- **Import** (`crates/formats/src/openapi.rs`) turns each operation into a request: realistic example bodies from the schema (examples, enums, formats, then property names), path parameters as variables (`{session_id}` → `{{sessionId}}`, generic names get the resource: `/pets/{id}` → `{{petId}}`) with their example values in the new environment. A document without a full server URL is refused with `needsBaseUrl` until the caller gives one.
- **Google Discovery documents** (`crates/formats/src/discovery.rs`) are turned into OpenAPI 3 whenever a document is parsed, so import, response checks, mocks and updates treat them like any OpenAPI document. Paths use `flatPath` (each segment its own variable), resources become tags (`users.messages`), and Google's OAuth 2.0 and API key become the `oauth2` and `apiKey` schemes. An OAuth 2.0 requirement that lists scopes asks for those, not every scope of the scheme.
- **Part of a document**: an `OperationFilter` (first tags, or paths) imports only some operations; `outline` lists a document's tags with their operation counts without building requests, for choosing.
- **The document is kept** in `specs/`; the imported folder links it (`openapi: {spec, source, validate, only, scheme}` in `_folder.yaml`: `only` is the part it took, `scheme` the security scheme chosen over the document's own) and each request names its operation (`openapi: {operation: "GET /pets/{petId}"}`).
- **Response checks** (`crates/formats/src/spec_check.rs`, `crates/api/src/specs.rs`): after each send, the status must be documented (exact, `2XX` or `default`) and a JSON body must match the documented schema (types, required fields, enums, `$ref`, `nullable`, `allOf`/`anyOf`/`oneOf`, lengths, ranges; formats and patterns are not checked). The result is a test, so it counts in runs, the CLI and JUnit reports. Parsed documents are cached until the file changes.
- **Update from a new version** (`crates/api/src/spec_update.rs`, `import.updatePreview` / `import.update`), keeping to the folder's `only` and `scheme`: new operations are added; for changed ones each field (method, URL, headers, body, parameters, auth, docs) takes the new version only where the saved request still has the old document's value, so the user's edits win; scripts, settings and names are never touched. Operations no longer in the document are kept and marked `removed` (crossed out in the sidebar). New path variables are added to the folder's environment (the environment named like the folder, the active one first when several are). Empty headers named like the one the folder's auth sends are left out, as an API catalog import leaves them out.

## API catalog
`crates/api/src/catalog.rs` (`catalog.list`, `catalog.preview`, `catalog.import`) imports well-known APIs in one step. The list is `crates/api/catalog/catalog.yaml`, compiled into the app; every entry names the publisher's docs page and, for downloads, the license. Sources:

- `download`: the publisher's OpenAPI, Swagger, Google Discovery, AWS Smithy (`crates/formats/src/smithy.rs`, one request per operation in the service's protocol, signed with SigV4) or Postman file, fetched only when the user imports it. Options: preset `groups` (huge APIs), the `scheme` to use, `secrets`, starting `variables`, a `baseUrl` when the document has none.
- `compatible`: an OpenAI-compatible provider: the OpenAI document's operations on the given `paths`, with the provider's `baseUrl` (responses aren't checked against OpenAI's schemas).
- `starter`: a description written for Zorvik (`crates/api/catalog/starters/`), for APIs that publish none.
- `graphql`: one GraphQL request with a sample query, auth and variables.
- `link`: not importable (the publisher's terms, or nothing machine-readable); the reason and the docs link.

Nothing third-party ships with the app. Downloads follow redirects (never from `https` to plain `http`), are capped at 50 MB and two minutes, and every failure (no connection, `404`/`410`, `401`/`403`/`429`/`5xx`, an insecure redirect, a web page instead of a file, an unreadable file) becomes a `catalogUnavailable` error that says what happened and how to download the file by hand and import it. Detecting and parsing a description runs off the async workers. The last download is reused for 15 minutes, so choosing groups (`catalog.preview`) and importing download once; an unreadable download isn't kept (trying again downloads again), and an imported one is let go. Preset groups the document no longer has are left out (with none left, the API comes whole, as the preview offers it). An import writes the folder (docs: description, docs link, source and license), activates its new environment and names the request to open first. The weekly `catalog.yml` workflow downloads and imports every entry (`crates/api/tests/catalog_live.rs`).

## Variables
Precedence, highest first: CLI `--var`, `pm.variables` (this send or run), the runner's data row, the active environment, workspace variables, globals, then dynamic values. In a scenario's run the first two layers are the scenario's: values given for the run and the current step's inputs, then the scenario's own values (see Scenarios). Values that scripts set on an environment, the workspace or globals are kept on this computer (`local-values.json`), never in the files, and win over the file value in their scope. Variables can reference variables (depth 10; cycles are reported). A name can be made of variables (`{{host.{{env}}}}`, inner first, as in Postman); each part is rendered once, so nesting stays linear, and an undefined one is reported as written, since the name it made can hold secret values.

Dynamic variables (`{{$uuid}}`, `{{$randomInt(1, 5)}}`) are one catalog in `crates/workspace/src/dynamic/`: every Postman name plus more, each a row with its group, description, example, argument form and generator. Requests, scripts (through the host) and mock server templates use it; the UI gets it in `app.info` for autocomplete, and a test writes the website's reference table from it. An unknown name or bad arguments leave the text as written and report it as undefined.

**In the UI**, environments are a sidebar section (`app/src/components/sidebar/EnvironmentsList.tsx`: workspace variables, globals, then the environments, with the active one's mark) and open in tabs (`VariablesTab` in `store/tabs.ts`, drawn by `components/environments/VariablesView.tsx`): a draft and what is saved, like a request, saved with `env.save` or `workspace.saveMeta`. `store/environments.ts` opens them (`showEnvironments`: the title bar's **Manage environments…**, Mod+E, an agent's `open_in_app`), creates, copies and deletes, and keeps open tabs in step with the workspace (a tab without edits takes a change made elsewhere; one whose file is gone says so). The list of open tabs is kept per workspace, but a variables tab's unsaved edits are not: they can hold secret values, which stay out of the window's storage. So before the tabs go for another workspace (`leaveTabs`: the workspace menu, entering the Bootcamp), the user is asked whether unsaved variables may be discarded.

## Networking
- **A fresh connection per request**, so DNS, connect and TLS are always measured. Timing phases: DNS, TCP connect (with the proxy tunnel), TLS, time to first byte, download.
- **DNS** uses the OS resolver (hosts file and VPN split DNS work); IPv6 and IPv4 race with Happy Eyeballs.
- **TLS** trusts the OS certificate store (Windows store, macOS keychain), so corporate inspection CAs work. An extra CA and client certificates (mTLS) are set globally in Settings; "don't verify" is available globally or per request.
- **Proxy**: system (environment variables, then the OS settings), none or manual, with Basic auth and a bypass list; localhost is always direct. PAC files, SOCKS and NTLM/Kerberos proxy auth are not supported.
- **Redirects** follow browser rules; `Authorization` and `Cookie` are dropped when the origin changes.
- **Limits**: response bodies are capped (100 MB by default) and decompression is bounded; WebSocket and gRPC messages up to 64 MB; stream lines and framed socket messages up to 16 MB.
- **HTTP/3** is opt-in per request or globally: `https://` only and never through a proxy.
- **gRPC**: `grpc://` (plaintext HTTP/2) and `grpcs://` (TLS), with server reflection or `.proto` files and every call type.
- **Other clients**: WebSocket, SSE, TCP (raw, line or length-prefixed framing, optional TLS), UDP, MQTT 3.1.1 and 5, DNS (UDP, TCP, DoT, DoH).

## Scripts
`crates/script` runs JavaScript in QuickJS. Each script gets a fresh runtime with no file or process access, a 64 MB memory limit and a time limit (Settings, 5 s by default). Input and results cross as JSON. The app's side is a `Host` (`crates/script/src/host.rs`, implemented in `crates/api/src/scripting.rs`) the prelude calls synchronously: `pm.sendRequest` sends through the engine with the app's settings and the AI agent's host guard (at most 100 per script, within the time left), `pm.cookies.jar()` reads and changes the jar for the request's own site only, and `{{$…}}` in `replaceIn` comes from the same dynamic-variable catalog as requests. After the script, the runner drains promise jobs, then timers in time order (sleeping until they're due), within the time limit. Scripts that use `await` run as an async function; exceptions in promise jobs, rejected promises nobody handled and a rejected top-level promise fail the script (a rejection tracker records them). `pm.visualizer.set` renders Handlebars in the sandbox; the UI shows the HTML in a script-less sandboxed frame.

The API follows Postman's sandbox (`crates/script/src/prelude.js`), so imported collections run unchanged: `pm.variables`, `pm.environment`, `pm.collectionVariables`, `pm.globals`, `pm.iterationData`, `pm.request` (with body modes, form fields and path variables), `pm.response`, `pm.test`, `pm.expect` (chai's BDD API, written in the prelude, behind a `Proxy` that rejects unknown words as chai does, with chai-postman's assertions on every assertion), `pm.execution` (`setNextRequest`, `skipRequest`, `location`), `pm.sendRequest`, `pm.cookies`, `pm.visualizer`, timers, `console`, `Buffer`, plus the legacy `tests[...]`, `postman.*`, `request`, `response…` globals. `pm.vault` and `pm.execution.runRequest` are not supported and say so. Variables are text between scripts, but a value a script sets that isn't text also travels as JSON (`VariableChange::json` → `Variables::typed`; not when nested over 100 levels deep, which serde_json can't read), so later scripts of the same send or run get the number, array or object back, as in Postman, while it still matches the text.

**SugarJS**: Postman loads SugarJS 1.3.9 (prototype extensions such as `String.prototype.has`) into every script. Loading it costs more than most scripts, so the prelude scans the script's source for the names it adds (the `SUGAR` table, checked against the library by a test) and defines only those it mentions as stubs that load it on first use; the library then replaces them. Postman's global `_` is lodash 3: the prelude adds lodash 3's names and call forms to lodash 4 when it loads.

**Libraries**: `require` (and `pm.require('npm:name@version')`, version ignored) gives the libraries of Postman's sandbox (lodash, crypto-js, moment, ajv, uuid, tv4, chai, csv-parse, xml2js, cheerio, sugar), browser versions of Node's `assert`, `buffer`, `events`, `path`, `querystring`, `url` and `util`, and the sandbox's own `timers`, `atob` and `btoa`; nothing else. `crates/script/vendor` bundles them with esbuild into one CommonJS file each (`dist/`, committed with `THIRD_PARTY_LICENSES.md`; its README says how to update them), so building Zorvik needs no npm. `src/libs.rs` includes the files, compiles each to bytecode once per process on first use (as a sloppy-mode script, not a module), and the prelude's `require` runs it in a Node-style module wrapper and keeps it for the rest of the run: a few milliseconds per library and run. Libraries get `crypto.getRandomValues` (from Rust's `rand`) and a private `process`/`Buffer`, never the host's (the global `Buffer` scripts see is hidden from libraries while they load). QuickJS is compiled with optimizations in debug builds too (`[profile.dev.package.rquickjs-sys]`): unoptimized, its stack frames are ten times larger and libraries such as ajv overflow the script stack.

## Responses
- **Bodies stay in Rust**: the last 30 response bodies (512 MB together) are kept by response id for **Save to file**, filters and examples.
- **Filters**: `response.filter` runs JSONPath (RFC 9535, `serde_json_path`) or jq (`jaq`) over the whole stored body (`crates/formats/src/filter.rs`); agents get the same through `send_request`'s `filter`. XPath runs in the web view (`app/src/components/response/filterModel.ts`) with the browser's XPath engine, on XML or HTML.
- **Offline tools** (`tools.*` in `crates/api/src/tools.rs`, run on a blocking thread): `tools.jsonDiff` (`crates/formats/src/json_diff.rs`: differences by RFC 9535 path, key order ignored, numbers by value, arrays aligned by their longest common subsequence up to 4M cells, else by index; or matched in any order), `tools.regexTest` (`crates/formats/src/regex_test.rs`: the `regex` crate with the captures' size limit, flags written inline, positions in UTF-16 units for the UI), `tools.certDecode` (`crates/engine/src/tools/certs.rs`: PEM blocks, DER or bare base64; certificates described like the TLS inspector's chain, a private key loaded with rustls/ring only to derive its public key and match it to certificates, never returned). `tools.recentResponses` / `tools.recentResponse` hand the tools the bodies of the last responses kept in memory (`recent_responses`). The UI keeps each tool's inputs and its last result in the tab with a revision number (`app/src/components/tools/live.ts`), so a result arriving after newer edits is dropped and switching tabs doesn't compute again.
- **Examples**: saved responses are part of the request file (`examples`, text bodies up to 1 MB). `response.text` hands the UI the whole body to keep; mocks built from requests answer with them (`crates/formats/src/mock.rs`); Postman responses import as examples.

## Console
`crates/api/src/console.rs` keeps the app-wide console: every request sent with what went out and what came back, and the lines scripts log, in the order it happened. It is one bounded list in memory per `Api` (5000 lines, 64 MB), never written to a file, cleared when another workspace opens.

- **Lines** (`ConsoleLine`) are small: a log line, or an exchange's method, URL, status, error, time and size. Each goes to the UI as a `StreamEvent::Console` event (emitted under the store's lock, so events arrive in id order); `console.list` gives the lines kept, so the list survives a reload of the window. The headers and bodies of an exchange (`ConsoleDetails`, bodies cut to 64 KB, binary ones without text) stay in Rust until the UI asks with `console.details`. Values are as sent, secrets included: that is what a failed request is debugged with.
- **Where lines come from.** A `ConsoleScope` (the console plus who is sending: the user, a collection run or an AI agent, and the request's name) travels in `SendContext`; `zorvik run` has none and logs nothing. `send_scripted_with` logs the request after it was sent: the response, or the error with the request as resolved (`Exchange::failed`), or as written when it couldn't be resolved (`Exchange::unprepared`). Scripts' console lines and failures reach it while the script runs through `Host::log` (the prelude calls it for each `console.*`), and `pm.sendRequest` requests from `AppHost::send`, so they stay in order. OAuth 2.0 token requests are made inside `zorvik_workspace::oauth2`: they are seen through the engine's `RequestOptions.observer`, set only for that call. Live connections (`ws.connect`, `socket.connect`, `sse.connect`, `grpc.*`, `mcp.connect`, `dns.query`) log how they opened or why not with `Api::console_connect`, and their closing; their messages stay in the tab's log.
- **Not logged:** load tests (their own client, by design: no cost on that path), the traffic of user servers, catalog downloads, imports from a URL and the update check.
- **UI:** `app/src/store/console.ts` applies events in batches and counts failures while the panel is closed; `components/console/ConsolePanel.tsx` draws the newest 300 matching lines (more on demand) and fetches details when a line opens.
- **Agents** read it with `read_console`, redacted like everything they get; token requests (`sensitive`) come without details. Each line keeps the secret values that were in use when it was logged (`ConsoleScope.redact`, shared by the lines of one scope, which can learn of more while it runs: a scenario's secret outputs and answers), so a value that changed since (a script that rotates a key, another workspace) stays hidden, and the tool's `search` matches the redacted text, so it can't be used to guess a secret.

## Collection runner
`crates/api/src/runner.rs` is shared by the app's Runner tab and `zorvik run`. It reads the requests of a folder once, then sends them in order for each iteration through the same scripted send as a single request (`send_item`, which a scenario's request steps use too). The app runs one at a time: collection runs and scenarios share the run slot (`RunnerState.active`), the `runner {runId}` events, `runner.stop`, `runner.details` and `runner.export`. CSV or JSON data files give one iteration per row. A request fails when it can't be sent, a script throws or a test fails; without tests, an HTTP status of 400 or more fails it. Reports are JSON or JUnit XML, and memory stays bounded on long runs.
- **Repeat until**: a request with `settings.repeat` is sent again, after `intervalMs`, until its condition holds (run as a hidden test after the post-response scripts; empty = until the request's tests pass), and fails after `timeoutMs`. The result shows the number of sends.
- **gRPC**: `scripting::send` calls `grpc::run_once` (descriptors from the request's `.proto` files or reflection, not cached) and `grpc::run_call`, which `grpc.invoke` uses for streaming methods too: unary calls send the message; streams send it (server streams) or run `grpc.onConnect` with `run_steps_once`, end the client side and read until `settings.stream` says to stop (stopping there ends the call as `OK`). `grpc::as_response` makes the answer an HTTP-like response: 200 for `OK`, else the HTTP status gRPC's code maps to, headers then trailers, and the message (unary) or the received messages as a JSON array (streams). In the app, `grpc.start` runs the steps on the open stream (`run_grpc_steps`, notes as `GrpcEvent::Info`).
- **Details**: each result carries `seq` and what it sent and got (`RunDetails`, bodies cut to 64 KB, secrets masked); the app keeps them for the last runs (64 MB together) for `runner.details`, and reports leave them out.
- **Event streams**: SSE requests are read until `settings.stream` says to stop (`crates/api/src/sse_read.rs`, shared with agents); scripts get `pm.response.events` and the events as text.
- **WebSocket and Socket.IO**: `scripting::send` calls `websocket::run_once` or `sockets::run_once_socketio`: connect, run the on-connect steps with `run_steps_once` (repeats don't run), close. Each wait becomes a `TestResult` (later ones skipped after a failure), notes go to the console, and the response is the handshake's answer (101 for WebSocket) with a JSON transcript of the messages as its body.
- TCP, UDP, MQTT and DNS requests are skipped, with the reason in the result.

## Scenarios
A scenario (`scenarios/<name>.yaml`, also in folders: `scenarios/Shop/Checkout.yaml`) runs saved requests as steps, with values passed from one to the next, checks, and flow. The model is `crates/formats/src/scenario.rs`: `Scenario` (variables, `steps`, `always`, data file, iterations, docs) and `Step` (name, `enabled`, `continueOnFailure`, and a `StepAction` tagged by `type`: request, if, forEach, repeat, parallel, set, wait, stop, scenario, script, ask). It also has what needs no network: `compare` (the comparisons of checks and conditions; numbers compare as numbers, `201` equals `"201"`), `JsonPick` (an RFC 9535 JSONPath that gives one value, or a list when the path can match several), step paths (`steps/2/else/0`, `always/0`; `Scenario::walk`, `step_at`), `retarget`, and `problem` (steps nested more than 16 deep, names that can't be variables). Value fields written as YAML numbers or booleans are read as text.

`crates/api/src/scenario.rs` runs them; `run` is shared by the app (`scenario.*`), `zorvik run --scenario` and agents.
- **Walker**: `Walker` goes through the step tree per iteration (`run_steps` and `run_step` are boxed, the tree recurses). A request step is `runner::send_item`, so scripts, tests, "repeat until", details and skip reasons are the collection runner's; then its checks become `TestResult`s and its outputs are read from the response (`Reader`: JSON path, header, cookie, regex, status, body, time). An output that finds nothing is a failed test unless `optional`. Every step returns a `Flow` (go on, leave the loop, end, failed, reached, stopped, overrun): a failed step ends the scenario unless the step or the scenario says to continue; `always` then runs (not after a user stop or "run to here").
- **Results** are `RunResult`s with a `StepInfo` (`step`: path, kind, depth, note, saved values), sent through a channel so nested steps report as they finish; `run` numbers, counts and keeps them like the runner. Steps that only hold or direct others (if, loops and their rounds, parallel, a called scenario) are rows too but count only when they fail (`StepKind::is_flow`, in `runner::count`, the UI's counts and JUnit). Reports are the runner's (`RunReport`, JUnit: request steps are suites by request path, other steps by name).
- **Values**: a scenario's values are `Variables.local` (typed values in `Variables.typed`, so scripts and loops get lists, numbers and objects back), and a request step's inputs go into `overrides` for that step (values given for the run stay on top). With `ScriptVars.scenario` both are data layers (`VarContext::push_data_layer`): their values are inserted as they are, never expanded as templates, so text a server answered can't pull in a secret; a dotted name reads into a JSON value (`{{item.id}}`, `{{items.0}}`, `{{items.length}}`). A value field is a template, or JavaScript after `=` (`Walker::expression`: one expression in the script sandbox, variables by name and in `vars`).
- **Nothing leaves the scenario**: what scripts set on the environment, the workspace or globals is moved into the scenario's values after each step (`Scope::absorb`), also `pm.environment.set` without an active environment (`ScriptVars::keeps_environment`); the app keeps none of it in `local-values.json`. Each iteration starts from the scenario's variables again, with the data row over them.
- **Secrets**: a value saved or asked for as secret is hidden in results (`Walker::shown`), and so are secret values inside other saved values (`mask_secrets`, also in `scenario.values`). `Walker::secret` also tells the run's console scope (`ConsoleScope::hide`), so agents read `{{name}}` for it in every line of the run, also the ones logged before it was known (the response it came in). A request step that is tried again puts its outputs back as they were before each new try.
- **Kept values**: what the last run left is kept per scenario in memory (`ScenarioState.kept`, secret names with it; cleared with the workspace) for `scenario.values`, `scenario.clearValues` and `RunMode::Only`. `RunMode` is `All`, `To(path)` (from the start up to a step) or `Only(path)` (one step with the kept values).
- **Flow**: `forEach` and `repeat` set the item and `index` and put the names back after the loop; every round is a row and counts as a step, and an iteration may run 10,000 steps. `parallel` gives each child a clone of the values and holds its results back, then reports them in order and merges what changed (`merge`: later child wins). A `scenario` step swaps in the other scenario's own values, runs its steps and `always`, and copies back the named outputs only (what its scripts set ends with it); a failed result of it (`Scope.failures`) fails the step, also when the other scenario went on after it; scenarios run each other at most 8 deep. The requests and scenarios a run needs are read when it starts (`collect`).
- **Asking**: an `ask` step calls `ScenarioPlan.ask`, which the app sets for runs the user started: it emits `RunEvent::Ask` and waits for `scenario.answer`. The command line and agents have none: the value comes with the run (`--var`, `variables`) or the step fails.
- **Files and folders** (`crates/workspace/src/scenarios.rs`): a scenario's id is its path under `scenarios/` without `.yaml` (`Shop/Checkout`), a folder's its path; every part is checked like a request path (no `..`, hidden names or symbolic links). Folders work like the collection's: `_folder.yaml` has the name and `seq`, and folders and scenarios of one folder share the order. `scenario.list` returns the tree (`ScenarioNode` with `folder` and `children`); `Workspace::list_scenarios` is every scenario, for lookups. `scenario.createFolder`, `renameFolder`, `deleteFolder` and `move` (a scenario or a folder, to a folder and a place) manage them.
- **Renames**: `item.rename` and `item.move` rewrite the request paths in scenarios (`retarget_scenarios`). Saving a scenario under a new name, or moving or renaming it or a folder it is in, gives it a new id: the steps that run it are rewritten in place (`Workspace::update_scenario`) and the values its last run left follow (`scenarios_moved`). The UI does the same for open tabs, their drafts too (`scenariosMoved` in `store/scenarios.ts`).
- **UI**: `app/src/components/scenarios/` (`ScenarioView`, `StepsEditor`, `StepFields`; `model.ts` has the pure parts: steps by path, moves, the values a step can use, problems), the saved list and kept values in `store/scenarios.ts`, and the run in `store/runner.ts` like a collection run's (`RunnerResults` draws both). Open tabs follow renamed requests in their drafts too. What a tab keeps by step path (open steps, where the latest run's results belong) follows steps that are added, removed or moved (`stepsMoved`: steps are the same objects until they change).

## Load testing
`crates/load` runs a plan on its own Tokio runtime so the app stays responsive.
- **Models**: virtual users (closed: send, wait, think, repeat) or arrival rate (open: requests start on schedule however slow the server is). In the open model latency is measured from the scheduled start, so a slow server can't hide its queueing.
- **Stages** ramp users or requests per second linearly; thresholds (`p50` … `p99.9`, `avg`, `max`, `errorRate`, `rps`) show pass or fail live and decide the result at the end. A threshold with `abortAfterSecs` is watched on every snapshot (the aggregator, every 250 ms, while the run is Running): once it has failed that long in a row, the aggregator cancels the run's stop token, and the run stops like a user stop and fails (`stoppedByThreshold` in the summary).
- **Client**: pooled HTTP/1.1 keep-alive and HTTP/2 multiplexing on the engine's connect path (DNS, proxy tunnel, OS-trusted TLS). Requests are resolved once; ones that use dynamic variables, data file columns or captured values, or signing auth (a fresh timestamp and nonce each time), are rendered per request (a render with every user variable set to a probe value tells which). Digest and NTLM can't be load tested: they answer a challenge on the connection that got it.
- **Per-user data**: `dataFile` (CSV or JSON, the runner's parser and file rules): virtual user N takes row N % rows for its life; in the arrival-rate model each request takes the next row. Precedence: `--var`, captured values, the row, then the environment.
- **Captures** (`json` path like `$.items[0].id`, `header`, or `regex` first group) save a value from a target's response for the same user's later requests; with captures each user sends the targets in their weighted order. A capture that finds nothing (or a value over 64 KB) keeps the old value and counts as a miss. Arrival rate: every request is its own iteration, so captured values are only checked, not reused.
- **Metrics**: an HdrHistogram per target and in total, 1-second buckets for the charts, snapshots to the UI four times a second. Timing phases too: connect (new connections only), time to first byte (server plus one round trip), transfer, and server-reported time from `Server-Timing` (its `total`, else the sum of `dur`). A warm-up (`warmUpSecs`) is applied in the recorder: samples that finish before it go into the 1-second buckets only, not the histograms or counters; throughput counts from its end. Virtual users draw a random think time per pause (`thinkTimeMaxMs`) from their own SplitMix64 generator, so the hot path takes no lock.
- **Safety**: a run against a host outside this computer and private networks asks first (hosts that come from the data file included). A rendered request must stay on the destinations known at the start (scheme, host, port and `Host` header), so a captured value can't move the load elsewhere. Dropped requests count as errors; `rps` leaves out the wait for requests in flight after the end. Caps: 5,000 users, 50,000 requests/s, 100,000 in flight.
- Run history (the last 30 runs per test) is kept in the app data folder, not the workspace. Runs export as HTML, JSON or CSV (per second and per request: `zorvik_load::seconds_csv` / `requests_csv`; text cells that a spreadsheet would run as formulas get a leading `'`). `zorvik load` exits with 1 when a threshold fails.

## Servers and mocks
`crates/servers` has one listener per saved server, reporting traffic through a `Reporter`; `crates/api/src/servers.rs` starts and stops them, applies live edits and keeps bounded logs. Every kind follows one contract: serve until `ctx.cancel`, read the latest settings from `ctx.live`, answer `ctx.control` (send, disconnect).

Kinds: **mock API** (routes with `:params`, templated bodies, delays, faults, matching on query, headers, body and JSON body conditions, answer sequences, CORS, forward to a real backend), **MCP**, **WebSocket**, **Socket.IO**, **SSE**, **TCP**, **UDP**, **DNS** and a **TCP relay** that logs both directions. The Socket.IO server (`crates/servers/src/socketio.rs`) is built on the mock's hyper stack with upgrades on: one task per Engine.IO session owns its namespaces and heartbeat, long-polling GETs and POSTs and the WebSocket only carry packets in and out, and the upgrade from polling to WebSocket (probe, noop, upgrade) moves a session's output to the socket. Templates can use environment and workspace variables but never secret ones, and text sent by clients is never expanded. WebSocket, TCP and UDP reply rules (`crates/servers/src/rules.rs`) match with `MessageMatcher` and fill in `{{message}}` and `{{message.path}}` after the variables; a WebSocket rule can close the connection with a code, and each WebSocket connection sends the server's scheduled messages on its own timer (no burst after a stall). A mock route with an answer sequence counts its calls in `Mock::calls`, keyed by the route's position plus a fingerprint of its method, path, status, conditions and sequence (reset on restart, bounded by the number of routes). The MCP server (`crates/servers/src/mcp.rs`) answers JSON-RPC from its settings (tools with schemas and templated results, resources and templates, prompts) over Streamable HTTP (sessions by `Mcp-Session-Id`, a `GET` stream per session for `list_changed` notifications when the settings change), HTTP+SSE (`/sse` and `/messages`), and stdio for `zorvik serve --stdio`, where the traffic log goes to standard error. A server starts with its workspace only if this computer already started or saved that exact configuration, and saving a running server applies the change to it.

## AI agents
Coding agents (Claude Code, Codex, Gemini CLI, Cursor and others) control Zorvik through MCP.

```
Agent ──MCP over stdio──► zorvik mcp ──127.0.0.1 TCP + token──► Zorvik app ──► Api ──events──► UI
```
- **`zorvik mcp`** is the MCP server the agent starts. It answers `initialize` and `tools/list` itself; on the first tool call it connects to the running app, or starts it and waits.
- **The app** listens on `127.0.0.1` (random port) and writes `agent.json` (port and token) to its data folder, readable by the current user only. Both sides prove they know the token with a SHA-256 over a fresh nonce; the token itself is never sent.
- **Headless** (off by default): when the app is closed, the tools run inside `zorvik mcp`. Nothing can be approved there, so actions that would ask are refused.
- **Permissions**, checked in Rust on every call: reading is allowed; edits (requests, folders, environments, servers, scenarios, load tests, files added with `write_file`) are allowed or asked (setting); requests to outside hosts are asked once per host and agent session; deletes, load tests, starting servers, reading files outside the workspace and opening workspaces always ask, and starting a program (an MCP request over stdio) asks every time. Settings, cookies and secret values are not available to agents; history, the console, variables, server traffic and everything returned have credentials redacted.
- **Input**: tools that save files (`save_requests`, `save_server`, `save_load_test`) refuse fields the model doesn't have, with the nearest known name ("did you mean `status`?"), so a typo is never saved silently. `save_scenario` checks its fields itself (`scenarios::unknown_fields`: the tagged steps hide unknown fields from serde) and names where each one is. Their JSON schemas document every field, unit and placeholder.
- **Tools** (`crates/api/src/agents/tools/`): workspace, requests (read several at once, save with query and path parameters), environments and variables (with values scripts saved), import and `update_from_openapi`, the API catalog (`search_catalog`, `import_from_catalog`: the download host is asked about like any traffic, and a huge API needs `groups`), `send_request` (HTTP, GraphQL, gRPC, DNS, MCP, SSE read to an end), live connections (`connections.rs`: `open_connection`, `send_message`, `wait_for_message`, `read_messages`, `close_connection` for WebSocket, Socket.IO, TCP, UDP and MQTT), collection runs, scenarios (`scenarios.rs`: `list_scenarios`, `read_scenario`, `save_scenario` (also into a folder), `move_scenario`, `run_scenario`, also up to a step or one step; a scenario is found by its id, or by a name only one has; an agent's run can't ask, so `variables` answers ask steps), GraphQL schemas, gRPC services, MCP catalogs (`mcp_catalog`), load tests, servers (`read_server`, `save_server`, `create_mock`, `start_server` with any port, `get_server_traffic`), `read_history`, `read_console`, `export_request` (cURL and code in 16 languages), `write_file` (up to 10 MB, not into Zorvik's own folders).
- **Live connections** an agent opens are ordinary `ws.*` or `socket.*` connections registered to its session (`AgentHub::sockets`); the tools read and wait on their `MessageLog`, with redaction and texts cut for the agent. `AgentEvent::Stream` attaches the connection to a tab when the user follows agents; its `opened` is an `Opened` (`StreamOpened` for WebSocket, `SocketOpened` for the others). A connection closes when its agent disconnects (a WebSocket with code 1001); closed ones stay readable (the newest 10 per agent) until then.
- **Where requests go**: each tool call runs in an agent scope. A host guard in the engine keeps every request (redirects, OAuth token requests, gRPC channels, DNS resolvers, collection and scenario runs) on the approved hosts. During an agent's call no files outside the workspace are read.
- **Visible**: the title bar shows the connected agent; the Agents panel lists every tool call; the app opens what the agent works on (setting).

Code: `crates/api/src/agents/` (sessions, confirmations, tool definitions and implementations), `crates/mcp` (JSON-RPC protocol, bridge, listener, `agent.json`).

## Training Bootcamp
The **Academy** is a course inside the app, opened from the pinned Training Bootcamp workspace (its title bar then has a Workbench | Academy switch); see [academy.md](academy.md) for the course format and how to write a lesson.
- **Course**: `crates/academy/course/` (a folder per unit, a Markdown file with YAML front matter per lesson), embedded at build time and validated by tests.
- **Labs**: `crates/api/src/academy/` saves the lab's servers into the Bootcamp workspace (`Lab · …`), starts them on free ports with the normal server manager, fills and activates the **Lab** environment, and starts practice servers from `crates/testkit` when a lab needs them. Progress saved before `knownLessons` existed knows the lessons without an `added` release in their front matter.

## Updates
The desktop app updates itself from GitHub Releases; nothing else is contacted and nothing about the user is sent.
- **`app/src-tauri/src/updates.rs`** wraps the Tauri updater: a check 20 seconds after start and every 6 hours, through the proxy from Settings. The places it reads are `SOURCES`, tried in order: a download that fails at one is tried at the next, and every file is verified by its signature wherever it came from. The state (`idle`, `checking`, `upToDate`, `available`, `downloading`, `ready`, `installing`, `failed`) goes to the UI as the `zv:update` event.
- **Settings → Updates** (`updates.mode` in `settings.json`): automatic downloads in the background and installs on quit; notify only shows a notice; off never checks.
- **Only signed updates install**: the signature must match the public key in `tauri.conf.json` and name the version.
- **Which copies install**: the Windows installer (NSIS), the macOS app in a writable folder, the AppImage. The portable zip, `.deb`, `.rpm`, a copy running from the disk image and debug builds only tell the user a new version is out.
- **Never an error for a failed update**: when a download, its signature check or the install fails, the status becomes `available` with `byHand`, and the notice links to the release page; that version isn't downloaded again until the next start. The reason goes to the log.
- **Restarting**: `update_install` stops servers and the agent listener, installs and restarts; the UI first lists what a restart would interrupt. On Windows the installer only closes the app itself, while `zorvik.exe` beside it is often still running (an agent's `zorvik mcp`): the installer's pre-install hook (`app/src-tauri/windows/hooks.nsh`) renames a `zorvik.exe` in use to `zorvik-old-<number>.exe`, which Windows allows for a running program, so the new one can be written; the old copy is deleted by a later install or the uninstall once nothing runs it. Otherwise a downloaded update installs on exit (`RunEvent::Exit`).
- **UI**: `app/src/store/updates.ts`, the notice in `app/src/components/UpdateNotice.tsx`, the Settings section in `app/src/components/modals/UpdateSettings.tsx`.

See [ci-release.md](ci-release.md#updates) for how `latest.json` is made and the signing key.
