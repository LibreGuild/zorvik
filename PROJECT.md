# Zorvik project rules

The one place for the rules of this repository, for people and for AI coding agents. `CLAUDE.md`, `AGENTS.md` and `GEMINI.md` only point here, so every agent reads the same rules. When you learn something the next person needs (a rule, a trap, a decision), write it in this file, not in an agent-specific one.

## What Zorvik is
An open-source desktop app for API and network testing: an API client (HTTP, GraphQL, gRPC, WebSocket, Socket.IO, SSE, MQTT, TCP, UDP, DNS), an MCP client and MCP servers for testing the tools AI agents use, collection runs, load tests, mock and test servers, a Training Bootcamp, and a `zorvik` command line. Coding agents control it through MCP (`zorvik mcp`).

Promises that shape every change:
- **Every feature is free.** No paid plans, no accounts, no cloud sync, none planned.
- **Local first.** Workspaces are plain files in a folder the user picks (share them through Git). Secrets stay in the app data folder.
- **Nothing is collected.** The only connection the app makes on its own is the update check to GitHub Releases (Settings → Updates), and it sends no data about the user. Don't add telemetry, analytics or other servers.
- **Coding agents are first-class.** Anything a person can do in the app, an agent should be able to do through MCP, with the same permissions and confirmations.

## Repository map
| Path | What |
|---|---|
| `crates/engine` | Networking only; knows nothing about files or the UI |
| `crates/workspace` | Workspace files, variables, auth, history, settings, secrets |
| `crates/formats` | Data model and import/export (cURL, Postman, OpenAPI) |
| `crates/api` | The RPC dispatcher (`Api::call`) and app state; agent tools in `src/agents/` |
| `crates/script`, `load`, `servers`, `mcp`, `academy` | Scripts, load generator, user servers, MCP, Training Bootcamp |
| `crates/cli` | The `zorvik` command line |
| `crates/testkit`, `devbridge` | Test servers; the API over HTTP for a browser (dev and E2E only) |
| `app/src` | React UI; `app/src-tauri` the Tauri shell (updater in `src/updates.rs`) |
| `docs/` | `architecture.md`, `ci-release.md`, `testing.md`, `academy.md`; `docs/pages` is the website and user docs |

Read `docs/architecture.md` before changing how parts fit together.

## Commands
```bash
cd app && npm ci && npm run tauri dev      # the desktop app with hot reload
cargo fmt --all --check
cargo clippy --all-targets -- -D warnings
cargo clippy -p zorvik-desktop --all-targets -- -D warnings   # the Tauri shell (not a default member)
cargo test                                 # also regenerates app/src/bindings and the dynamic variables docs (commit them)
cd app && npm run typecheck && npm test && npm run e2e
cd app && npm run package -- --bundles app # macOS: Zorvik.app with the CLI inside
cd docs/pages && npm ci && npm run build && npm run check   # website and its links
```
E2E needs `cargo build -p zorvik-cli` once. Ports it uses: test servers 18787, dev bridge 18799, Vite 15420 (see `docs/testing.md`).

## Rules
**Code**
- Match the code around you: naming, comment density, error style. Keep changes focused.
- Put logic where it belongs (see the map). The UI renders state and calls `rpc`; behaviour lives in Rust.
- `app/src/bindings/*.ts` and the variable table in `docs/pages/…/variables/dynamic-variables.md` are generated by `cargo test`; never edit them by hand.
- Messages and labels are for users: plain words that say what happened and what to do next.
- Keep Rust crate versions and npm package versions of Tauri in step (`tauri` in Cargo.lock and `@tauri-apps/api`/`cli` in `app/package.json`), or `tauri build` refuses. The signer in `ci.yml` (`sign-updates`) is pinned to the same CLI version.

**Tests**
- Every fix or feature gets tests: Rust next to the code or in the crate's `tests/`, Vitest for UI logic, Playwright for user flows.
- Prefer real servers on `127.0.0.1` (`crates/testkit`) over mocks.
- All checks in the Commands section must pass before a PR.

**Docs** (same change as the code)
- User-facing change: the in-app docs (`app/src/components/docs/content.ts`), the website docs (`docs/pages/src/content/docs/docs/`), the README when it changes what Zorvik is, and a line under `Unreleased` in `CHANGELOG.md`.
- Design, build or release change: `docs/architecture.md`, `docs/ci-release.md` or `docs/testing.md`.
- Docs read like a finished product: no internal history, phases or roadmaps.

**Security**
- Workspace files come from Git and are untrusted input. Requests carry secrets: keep them out of files, logs, errors and agent output.
- Agent tools check permissions in Rust on every call; never add a tool that skips them.
- Never print, commit or log keys, tokens or passwords (including the updater signing key and its password, which live only in GitHub secrets).

**Git and releases**
- Work on a branch; `main` changes only through reviewed pull requests (squash merge).
- AI agents: don't commit, push, open PRs, create tags or publish releases unless the maintainer asks in that session.
- Releases come from `vX.Y.Z` tags that match the version (`cd app && npm run set-version -- X.Y.Z`); see `docs/ci-release.md`.

## Notes
Things that cost time once. Add to this list when you hit a new one.
- `Api::call` returns a boxed future; long `match` arms inflate the stack in debug builds, so the Academy harness spawns solutions instead of awaiting them inline. The same goes for big futures awaited inside one arm (an MCP connect): `Box::pin` them, or agent tests overflow the stack.
- MCP requests that start programs: workspaces are untrusted, so check `mcp::check_program` (or ask, for agents) before anything spawns; never add a path that starts a workspace's program without it.
- In E2E, pick CodeMirror completions by clicking: it ignores Enter for 75 ms after the list opens.
- Tests that use the OS trash run only with `ZORVIK_TEST_TRASH=1`.
- Updates are signed with the project's updater key: the public key is in `app/src-tauri/tauri.conf.json`, the private key only in the GitHub environment `release`, which only `main` and `v*` tags can use, and only the `sign-updates` job reads it (see `docs/ci-release.md`). Never change the public key casually; installed copies stop accepting updates. `ZORVIK_UPDATE_URL` points a build at a local `latest.json` for testing.
- Starlight sidebar groups that autogenerate need `{ label, items: [{ autogenerate }] }`.
- The website's main site is built from the latest release; `main` goes to the preview at `/zorvik/next/`. So docs changes go live on the main site with the next release (`docs/ci-release.md`, Website).
